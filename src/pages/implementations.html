Razor

maintained

Razor is a modernised occam / occam-π toolchain forked from KRoC. It keeps KRoC's proven components and brings them up to date for current systems:

  • real 64-bit support, with native code for x86-64 and AArch64 on macOS and Linux (Apple Silicon included);
  • the Transterpreter virtual machine as a fallback for other CPUs;
  • old K&R C modernised, the tree tidied up, build scripts moved to Python 3, and more regression tests;
  • the full occam-π language and KRoC's libraries, including the course module used by the tutorials on this site.

Its parts: occ21 (the occam compiler, descended from the Inmos compiler), tranx86 (translates compiler output to native code) and CCSP (the fast CSP scheduling kernel). Tools are GPL-2+ and libraries LGPL-2+.

You need GCC or Clang with binutils, pkg-config, xsltproc and Python 3. SDL, OpenGL and libpng are optional, for the graphics libraries. Write your first program →

SPoC: Southampton Portable occam Compiler

archived source

SPoC was written at the University of Southampton by Mark Debbage, Mark Hill, Sean Wykes and Denis Nicole, and presented at WoTUG-17 in 1994. It translates occam 2 into portable ANSI C, so occam can run on any machine with a C compiler. The generated code implements occam's processes and channels with a small, efficient scheduler, and it can call and be called from C.

SPoC's direct translation to C still makes it a good base for embedding occam in C projects, for teaching, and possibly as a route to running occam in the browser via WebAssembly (see the playground plans).

  • WoTUG SPoC archive: source for v1.1 (1994) and v1.3a (1998), with the OUG-17 paper.
  • The original Southampton page (archived). It lists versions 0.9e to 1.3, including Windows 95 and Linux builds.
Help wanted. SPoC has no modern public repository. A maintained version that builds with current C compilers would be very welcome. See contributing.

KRoC: Kent Retargetable occam Compiler

upstream

KRoC came out of the EPSRC occam For All project at the Universities of Kent and Keele in the mid-1990s. Its first public release (0.9β) is dated 1997. It took the Inmos occ21 compiler, translated its transputer code to native x86 code, and ran it on CCSP, a very fast user-level scheduler. Context switches and channel communications took tens of nanoseconds, which made millions of processes practical.

KRoC was the testbed for occam-π and taught concurrency at Kent for many years. Development moved to GitHub, where the upstream repository is still available.

  • github.com/concurrency/kroc: upstream KRoC
  • github.com/concurrency/occam-compiler: occ21 on its own
  • Kent KRoC page: classic releases up to 1.4.0 (2006)
  • occam-pi.org and the OccamDoc library reference

The Transterpreter

portable VM

The Transterpreter (TVM), by Christian Jacobsen and Matt Jadud, is a small, portable virtual machine that runs transputer bytecode produced by the occam compiler. It is written in portable C, so occam-π ran on LEGO Mindstorms, the Cell processor, Arduino (as Plumbing) and other small devices. It is part of both KRoC and Razor.

  • transterpreter.org (archived)
  • concurrency.cc: occam-π on Arduino

The Inmos toolset

historic

Inmos's own occam 2 compilers (the oc / occ2 family) and the Transputer Development System produced code for the transputer. Their sources were later released and are preserved by WoTUG. KRoC's occ21, and so Razor's, descends directly from them.

occam-π in brief

occam-π keeps occam 2.1's safety rules and adds features for building systems whose shape changes while they run. Mobile values move ownership instead of copying, so there is no aliasing. Channel ends can be sent down other channels, so the process network can be rewired at run time. FORK starts a new process.

Further reading: Welch & Barnes, Communicating Mobile Processes: introducing occam-π (2005), and Fred Barnes's occam-π extensions tutorial (archived).

The occam 3 draft

Geoff Barrett's occam 3 Reference Manual (draft, 31 March 1992) was Inmos's plan for the language's next generation. It was written with the T9000 and its virtual channels in mind. Its main proposals:

  • Call channels, which package a request and its reply as one remote-procedure-style communication;
  • shared channels, so many clients can use one server safely;
  • modules and libraries with explicit interfaces;
  • user-defined data types and records (later adopted in occam 2.1).

SGS-Thomson did not fully implement occam 3. occam 2.1 took its type system, and occam-π later provided shared channels (SHARED/CLAIM) and channel types that do what call channels were meant to. The draft is still worth reading as a design document.

Future directions. We plan to collect proposals for the language's future here, such as extensions in Razor and NOCC and ideas from CPA papers. Get in touch if you have one.
