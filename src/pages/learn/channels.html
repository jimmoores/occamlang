Lesson 2 of 4

Processes & channels

Run things at the same time and let them talk. This is the core of occam.

PAR

PAR runs its components at the same time, and finishes only when all of them have finished:

PAR
  x := f (a)
  y := g (b)

The compiler checks the usage rules. A variable assigned in one branch of a PAR must not be read or written in any other branch. Change the second line to y := g (x) and the program does not compile. Data races are compile-time errors in occam, not bugs you find later.

Channels

So how do parallel processes share information? Over channels. c ! e sends the value of e; c ? x receives into x. A channel is:

  • synchronous: the sender waits for the receiver and the receiver waits for the sender. The value passes at the moment both are ready, with no buffering;
  • point-to-point: exactly one process writes and one reads;
  • typed: CHAN INT, CHAN BYTE, or a PROTOCOL for structured messages.

The main process is exactly the diagram. It declares the channel c and runs the two processes in PAR, giving one the writing end (c!) and the other the reading end (c?). Each diagram box is a process instance, and each arrow is a channel declaration.

Your first deadlock

Synchronous communication means processes can wait for each other forever. The classic case is two processes that each insist on sending first:

CHAN INT a, b:
PAR
  INT x:
  SEQ
    a ! 1          -- waits for someone to read a ...
    b ? x
  INT y:
  SEQ
    b ! 2          -- ... while this waits for someone to read b
    a ? y

Neither output can complete, so nothing happens. KRoC and Razor detect that every process is blocked and report the deadlock. Two ways to fix it:

  • reorder one side, so it receives first, then sends;
  • do both halves in parallel: PAR (a ! 1, b ? x), written one per line.

Deadlock is not a mysterious run-time accident in occam. It is a property of the process network, and you can design it out with patterns such as client-server and I/O-PAR, or prove it absent with FDR.

Protocols

A channel can carry structured messages. A sequential protocol sends several values as one communication. A variant protocol sends tagged alternatives:

PROTOCOL READING IS INT; REAL64:      -- sensor id, value

PROTOCOL CONTROL
  CASE
    set.rate; INT
    reset
    stop
:

PROC logger (CHAN READING in?, CHAN CONTROL ctl?)
  ...
:

ctl ? CASE with one branch per tag receives a variant message. You will see it with ALT in lesson 4.
