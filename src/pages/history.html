History & foundations

Where occam came from

A language built for a chip and derived from an algebra. This page tells the story, from Hoare's 1978 paper to the compilers you can download today.

Origins at Inmos

Inmos was founded in Bristol in 1978 with backing from the British government. Its plan was to build a new kind of microprocessor, the transputer: a complete computer on one chip, with processor, memory and serial communication links, designed so that many of them could be wired together into one parallel machine.

Such a machine needed a language that treated concurrency and communication as basic operations, not as library calls added later. David May led the design of that language at Inmos, with Tony Hoare as a consultant. The result was released in 1983 and named occam after William of Ockham, the fourteenth-century friar whose "razor" says that entities should not be multiplied beyond necessity.

The name fits. occam 1 had a small set of primitive processes (assignment, input, output, SKIP, STOP) and a few constructors (SEQ, PAR, ALT, IF, WHILE). The language and the transputer were designed together, so a channel communication in a program became one or two machine instructions on the chip.

Primary sources. The earliest surviving design document, Proto-occam (July 1983), is among the occam books on transputer.net. Inmos Technical Note 8, The Implementation of occam on the IMS T414 (1985), shows how the language mapped onto the silicon.

The CSP foundation

In 1978 Hoare published Communicating Sequential Processes in Communications of the ACM. It proposed that input and output are primitive operations, that parallel composition of sequential processes is the way to structure programs, and that processes communicate by synchronised message passing with guarded choice between alternatives.

Through the early 1980s, Hoare, Stephen Brookes and Bill Roscoe at Oxford turned CSP into a mathematical theory. The failures model (JACM, 1984) and then the failures-divergences model gave precise meanings to deadlock, livelock and refinement. Hoare's 1985 book, Communicating Sequential Processes, set out the theory in full.

occam is close to a concrete syntax for CSP. The correspondence is:

occamCSPmeaning
c ! e / c ? xc!e → P / c?x → Psynchronised output / input
SEQP ; Qsequential composition
PARP || Qparallel composition, synchronising on shared channels
ALTP □ Qexternal choice between guarded alternatives
STOP / SKIPSTOP / SKIPdeadlock / successful termination

Because of this correspondence, occam programs obey algebraic laws. Roscoe and Hoare's The Laws of occam Programming (1988) gives a set of equations, such as the associativity of PAR and the distribution of SEQ over IF, that is complete enough to reduce any finite occam program to a normal form. Inmos used this kind of reasoning in practice: the T800's floating-point unit was verified using formal methods, one of the first industrial uses of formal methods on hardware.

Language versions

occam 1 (1983) had one data type, the word-sized integer, and untyped channels. It was deliberately minimal.

occam 2 (1987) made it a practical systems language. It added typed channels with protocols, BYTE, BOOL, fixed-width integers and IEEE floating point, arrays, functions and VALOF, and the usage rules that let the compiler reject aliasing and parallel write conflicts.

occam 2.1 (1994) added named data types, records, RETYPES and RESHAPES, and other conveniences. It is the last version standardised by the chip vendor (reference manual, PDF).

occam 3 was a larger redesign, drafted by Geoff Barrett in 1992. It included shared channels (call channels), modules and libraries, and user-defined types. It was never fully implemented, but many of its ideas returned in occam-π. (draft manual, PDF)

occam-π (2000s), developed mainly by Peter Welch and Fred Barnes at Kent, adds ideas from Milner's π-calculus to occam 2.1: mobile data and channel ends, dynamic process creation with FORK, BARRIERs, shared channels with CLAIM, and recursion. Its compiler checks these features so they keep the language's safety guarantees.

Folding editors

occam programmers at Inmos usually worked in a folding editor. The Transputer Development System (TDS) had no separate file browser. The whole program was one hierarchy of folds: a closed fold appeared as a single line ... comment. You entered it to see its contents, which ran from a {{{ line to a }}} line. Because occam uses indentation for structure, a fold is always a complete process or declaration. That made folds a natural unit for thinking about a program as well as for editing it.

This site uses the same convention. Each section is a fold, and so is each code listing that contains ... lines. Try it:

PROC server (CHAN INT in?, out!)
  {{{! local state
  [100]INT table:
  INT count:
  }}}
  SEQ
    {{{! initialise
    count := 0
    SEQ i = 0 FOR SIZE table
      table[i] := 0
    }}}
    WHILE TRUE
      {{{ serve one request
      INT n:
      SEQ
        in ? n
        out ! table[n]
      }}}
:

The idea outlived the TDS. Later occam editors (the origami folding editor) and fold modes for Emacs and Vim kept the {{{ }}} markers, and they are still the default fold markers in Vim. WoTUG kept a page on folding editors.

Process diagrams

occam people design with pictures. In the style Peter Welch developed for teaching at Kent, each process is a box and each channel is an arrow from writer to reader. A box can hold a whole network of processes, so diagrams nest the way folds do. The picture maps directly onto a PAR of instances wired together by channel declarations, so you can write the code straight from the diagram.

Welch's "Legoland" (small, reusable processes such as id, succ, plus, delta and prefix, composed into numbers, integrate and pairs) is still one of the best introductions to concurrent design. Work through it here →

His lecture notes also had a recognisable handwritten style: occam keywords written in lower case and underlined rather than capitalised. The SEQ/seq button in the header shows every listing on this site in that style.

Descendants
  • XMOS xCORE and XC. David May co-founded XMOS in 2005. Its multi-threaded processors have hardware channels and events, and its XC language brings occam's model to C.
  • Go. Goroutines, channels and select come from the same CSP line as occam. The Go FAQ names occam and Erlang as "two well known languages that stem from CSP". Rob Pike's route to Go ran through Newsqueak, Alef and Limbo (Russ Cox's history).
  • JCSP, C++CSP, PyCSP and others. CSP process libraries for mainstream languages, many developed by the WoTUG/CPA community.
  • Handel-C. occam's model compiled directly to hardware. See hardware.

For a wide survey, see Øyvind Teig's taxonomy of CSP-based systems.
